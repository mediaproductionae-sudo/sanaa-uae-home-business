# الأدوار وRLS والتخزين

كل الجداول العامة الخمسين مفعّل عليها RLS وتملك سياسة قراءة. سُحبت الصلاحيات الافتراضية قبل إضافة صلاحيات محددة. لا توجد كتابة مالية أو صلاحيات أدوار أو تعديل حالة ترخيص من `anon` أو `authenticated`، حتى للمسؤول من المتصفح.

| الدور | نطاق القراءة | الكتابة المباشرة المسموحة في 4A |
| --- | --- | --- |
| Anonymous | فئات فعالة، متاجر فعالة لبائع فعال، منتجات منشورة غير مخفية وصورها | لا شيء |
| Customer | ملفه وأدواره وعناوينه وسلته وطلباته ودفعاته وشكاواه وإشعاراته | اسم العرض، حقول عنوانه، علامة قراءة إشعاره فقط |
| Seller | نطاق العميل إن كان عميلاً، ومتاجره ومسوداته وطلباته الفرعية وعمولاته وتسوياته فقط | اسم/وصف منتجه، بيانات عرض متجره، رفع مستند كمسودة وملف داخل مسار متجره |
| Admin | وفق مفاتيح `admin_permissions` الصريحة، وليس الدور وحده | لا كتابة مالية من العميل؛ التغييرات المؤثرة تحتاج خدمة خادمية لاحقاً |
| License Reviewer | المتاجر والمستندات الخاصة للمراجعة، دون الدفعات أو ملفات الأشخاص | لا اعتماد ترخيص مباشر؛ مسار المراجعة المُدقق في 4B |
| Complaints Officer | المتاجر والشكاوى والملاحظات الداخلية؛ لا مالية | خدمات الإجراءات في دفعة لاحقة |
| Delivery Operator | شركاته الفعالة وشحناتها ذات التخصيص الحالي لها فقط وعقودها وتسوياتها | لا تأكيد توصيل أو تعديل تسوية من العميل |

مفاتيح الإدارة: `users.read/manage`, `stores.read/manage`, `licenses.review`, `catalog.manage`, `orders.read`, `complaints.manage`, `delivery.manage`, `finance.read/manage`, `audit.read`.

الدوال المساعدة في `app_private` تستخدم `SECURITY DEFINER` فقط للقراءة المحدودة والتحقق، وتثبت `search_path=''` وتؤهل أسماء الجداول. تعتمد على `auth.uid()` ولا تستقبل userId بديلاً عن هوية الجلسة. لا تُكشف `app_private` في Data API. دوال triggers ليست قابلة للتنفيذ بواسطة PUBLIC.

المالك/service_role يتجاوز RLS لأسباب تشغيلية، ويُحفظ خارج المتصفح. لذلك يجب فرض الصلاحيات في خدمة كل أمر قبل استعماله. القيود المالية الأساسية وtriggers append-only تعمل حتى مع كتابة الخدمة؛ مالك قاعدة البيانات المميز يستطيع تغيير DDL، ولذلك حماية التطبيق لا تعني عدم قابلية قاعدة البيانات للتلاعب من مسؤول بنية تحتية. الإنتاج يحتاج صلاحيات تشغيل محدودة ونسخاً احتياطية ومراقبة وتصدير سجل مستقل.

## Storage

- `catalog-media`: خاص، صور PNG/JPEG/WebP حتى 5MiB. لا SVG أو HTML. القراءة العامة فقط للصورة المسجلة لمنتج ظاهر، والرفع داخل مسار UUID متجر يملكه المستخدم.
- `store-documents`: خاص، PDF/PNG/JPEG حتى 10MiB، لمالك المتجر أو مراجع التراخيص فقط.
- مسار كل ملف يبدأ بـ `store_uuid/` ثم اسم عشوائي. لا overwrite/delete من واجهة المستخدم؛ النسخة الجديدة بمسار جديد. التنظيف والفحص الضار ومطابقة MIME الحقيقي وPDF scanning وخفض EXIF وإصدار الروابط المؤقتة مسؤولية خدمات 4B.
- انتهاء رابط موقّع سبق إصداره وتخزين CDN يحتاجان TTL قصيرة وسياسة إبطال عند تعليق منتج؛ RLS لا يبطل تلقائياً كل رابط وقع مسبقاً.
- حدود الحجم/MIME موجودة كإعداد bucket، لكن اختبار HTTP الفعلي لرفع Storage لم يُنفذ في 4A.

## نقاط لا تُستبدل بقيود الصف

RLS يعزل الصفوف، وGRANT على الأعمدة يحمي الحقول المحمية. لا تحوّل جدولاً مالياً إلى writable لسهولة بناء الواجهة. وظائف الشراء والدفع والاسترداد والتسوية والتخصيص في مراحلها يجب أن تملك معاملات وقفل صفوف وبصمات طلبات، وتعيد DTO محدداً دون بيانات بائع آخر. لا تستخدم view افتراضية تتجاوز RLS؛ أي view لاحقة تكون security_invoker أو تُفحص صراحة.
