# ترحيل البيانات وخطة 4B–4F

## جرد الحالة المحلية

`components/demo-state.tsx` يحتوي: المستخدم المحلي، المفضلة، السلة، المتاجر والمنتجات وصورها base64، ملكية المتجر المحلية، الطلبات ولقطات الأسعار، الشكاوى والردود، الرسائل والتقييمات، الإشعارات والتفضيلات. `gov` يحوي جلسة ودوراً تجريبيين، وحالات المراجعة والإخفاء والشكاوى والسلامة، وقواعد العرض وسجل localStorage.

هذه كلها بيانات عرض/اختبار. لا تنشئ منها auth.users أو user_roles أو admin_permissions، ولا تستورد جلسة `gov.session/actor` أو user.role أو كلمات مرور أو تراخيص باعتبارها هوية حقيقية. الأرقام التجارية القديمة ليست دفعات أو مستحقات أو أرصدة افتتاحية حقيقية.

## مسار انتقال اختياري آمن

1. اجعل المستخدم يصدر JSON محلياً بإرادته، دون تحميل تلقائي. احفظ النسخة الأصلية ولا تمسح مفاتيح v2/v3/v4.
2. في 4B افحص المخطط والحجم وأطوال النصوص والأنواع والصور وMIME والبيانات الشخصية. احسب hash للمحتوى وسجل import batch. اعرض dry-run وعدد العناصر والتحذيرات؛ لا SQL ناتج من النصوص.
3. يدّعي المالك الجديد ملكية الكتالوج فقط بعد Auth حقيقي ومراجعة صلاحية. أنشئ mapping من أرقام demo إلى UUID. لا تكتسب المتاجر حالة active أو license approved من JSON.
4. استورد صوراً مفحوصة إلى buckets خاصة، وفئات وبيانات منتجات كمسودات، ضمن transaction للبيانات مع عملية معالجة ملفات قابلة للاستعادة. unique source_hash يمنع استيراد نفس الدفعة مرتين؛ تحقق من server-generated mapping كذلك.
5. أبقِ الطلبات/المدفوعات/العمولات/التسويات المحلية أرشيف demo منفصلاً للقراءة فقط. إذا احتاج النشاط أرصدة حقيقية افتتاحية، يلزم مسار محاسبي موثق وموافق عليه، لا تحويل حالة الطلب المحلي إلى paid.
6. تحقق من الأعداد والملكية والصور والتراجع واستئناف العملية. بعد النجاح يقرر المستخدم الاحتفاظ بنسخته المحلية أو حذفها يدوياً. لا مسح تلقائي في 4A ولا 4B.

في 4A يوجد schema `import_batches` وخطة فقط؛ لم تُنشأ أداة استيراد تجاري ولم تُرفع بيانات متصفح أحد.

## بوابات المراحل

| الدفعة | التنفيذ المخطط | شرط القبول قبل الانتقال |
| --- | --- | --- |
| 4A الحالية | SQL/RLS/أنواع/علاقات/قيود/seed/اختبارات قاعدة/خطة نشر | مراجعة التقرير؛ اتصال staging وAPI/RLS حقيقي لا يزالان مطلوبين |
| 4B | Supabase SSR/Auth وملفات profiles وأدوار آمنة وكتالوج متصل، خادم Node، pagination والتحقق وحد العمليات، bootstrap إدارة، مستندات خاصة | حساب عميل وبائع حقيقيان في staging، تأكيد البريد وتجديد الجلسة، عزل JWT حقيقي بين حسابين، منع الترقية الذاتية، Storage خاص، SSR وcallback على المضيف المختار |
| 4C | سلة DB وعناوين وcheckout متعدد البائعين وRPC ذري وحجز مخزون ومنع تكرار وإلغاء قبل الشحن | اختبارات مخزون متزامنة وrollback وتطابق المجاميع وبصمة idempotency وتثبيت السعر، وعدم قبول سعر العميل |
| 4D | لوحات شركات التوصيل وعقودها وتغطيتها وتسعيرها ومحرك تخصيص وإثبات موثوق | استبعاد غير المؤهل قبل الترتيب، منطقة الطرفين ونوع المنتج والوزن/الحجم والسعة، تعادل ثابت، عدم وجود شركة، عروض مؤرخة وأسباب قابلة للتدقيق |
| 4E | حساب العمولة المزدوجة وأحداث أهلية/حجز وledger وتسويات جزئية وتصحيحات | 10% تجريبية فقط، fixed/percentage/hybrid، استبعاد التوصيل من عمولة البيع، توزيع المبالغ والضرائب/رسوم البوابة منفصلة، تزامن التسوية، عدم التكرار، الحجز والعكس والحدود التراكمية |
| 4F | محاكي دفع محمي وProvider Adapter وتوقيعات أحداث واسترداد كامل/جزئي وربط اللوحات | نجاح وفشل وانتهاء وإلغاء وإعادة أحداث وتعارض payload وسباق capture/refund وحدود مبلغ/كمية الاسترداد، تدقيق دفاتر ومراجعة شاملة للـ RLS والاستضافة والواجهات |

لن يبدأ أي بند من 4B–4F في هذه الدفعة، ولن يُفعل دفع حي أو شحن API حقيقي. كل دفعة تحتاج موافقة المالك قبل بدايتها. لا تُسمى صلاحيات SQL واختبارات البنية بديلاً عن فحص أمان الإنتاج واختبارات تكامل مزود الدفع/التوصيل.
