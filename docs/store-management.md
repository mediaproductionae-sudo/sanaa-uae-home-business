# حفظ المتجر وحذفه

## الواجهة الحالية

- يحفظ «حفظ المتجر» التعديل، أو ينشئ المتجر مباشرة إذا كان نموذج إنشاء متجر جديد مفتوحاً. بعد نجاح الحفظ يعود العرض إلى أعلى محتوى «متجري»، حيث تظهر رسالة النجاح وأزرار الإدارة، وينتقل التركيز إلى عنوان القسم. احترام إعداد تقليل الحركة قائم.
- زر «إنشاء متجر» يفتح نموذج متجر آخر؛ ليس خطوة ثانية لاعتماد متجر حُفظ بالفعل.
- يقبل بريد التواصل أي عنوان صحيح بدلاً من اشتراط نطاق example.test. لا يرسل التطبيق رسائل إلى هذا البريد ضمن هذا التعديل.
- بجانب زر الإنشاء يوجد «حذف المتجر». تعطيله أثناء إدخال متجر جديد يمنع حذف المتجر السابق عن طريق الخطأ، ويتعطل أيضاً إذا لم يوجد متجر محدد.
- الحذف يفتح حوار «هل أنت متأكد من عملية حذف المتجر؟». الإلغاء وEscape لا يغيّران البيانات؛ التأكيد يزيل المتجر التشغيلي ومنتجاته من العرض والسلة والمفضلة.
- تبقى سجلات الطلبات والشكاوى والتقييمات والمراسلات. تُستكمل اللقطات التاريخية الناقصة من الكتالوج قبل إزالته، دون تغيير السعر التاريخي أو حالة الطلب.
- بعد حذف آخر متجر تظهر حالة فارغة واضحة، ويمكن إنشاء متجر جديد. لا يُختار متجر يملكه مستخدم آخر تلقائياً.
- تبقى الهوية واللغة والسلة الخاصة بالمنتجات الأخرى محفوظة. تحفظ هوية المتجر المحذوف الدنيا في deletedStores لتظل الشكاوى وأسماء المتاجر التاريخية قابلة للعرض بعد إعادة فتح المتصفح.

## مدخل Supabase / Node

المهاجرة `202611190006_store_removal.sql` تضيف RPC محددة لأرشفة متجر يملكه مستخدم مؤكد ونشط. تتحقق من الملكية، وتقفل سجل المتجر وتعيد التحقق منها، ثم تؤرشف المتجر ومنتجاته ضمن معاملة واحدة وتسجل التغييرات. لا تحذف سجلات مالية أو طلبات أو شكاوى ولا تغيّر سياسات RLS القائمة.

تُستبعد المتاجر المؤرشفة من قائمة إدارة البائع، ويُرفض تعديلها أو إضافة منتجات إليها عبر RPCs البائع، كما يمنع مسار الرفع إرفاق ملفات جديدة بها. لا تستهلك المتاجر المؤرشفة حد المتاجر التشغيلية الخمسة. ملفاتها وسجلاتها المرجعية محفوظة وفق الصلاحيات القائمة، وليس حذفاً مادياً للجداول أو لملفات Storage.

في Node، يعيد الحفظ المستخدم إلى أعلى الصفحة عبر التحويل بعد نجاح المعاملة. الحذف يحتاج تأكيداً، ثم يستدعي API خادمية بعميل جلسة المستخدم؛ لا يستخدم service_role لتعديل المتاجر. تظهر رسالة واضحة بعد العملية. أُضيفت أيضاً حقول ترجمة المتجر إلى نموذج Node للحفاظ عليها عند حفظ البيانات.

**لم تُطبّق المهاجرة على Supabase مستضاف.** يلزم تطبيق المهاجرات بالترتيب واختبار JWT فعلي عند إكمال اتصال Node. الموقع المنشور الحالي ما زال يستخدم مخزنه المحلي كما كان.

## التحقق الفعلي

- TypeScript وبناء الموقع ومدخل Node: نجحت.
- اختبار الحالة: الملكية، عدم تعديل نسخة الإدخال، تنظيف كتالوج المتجر فقط، السلة والمفضلة، بقاء السعر والحالة وسجلات الشكاوى، الاختيار التالي وسجل العمليات.
- المتصفح: 1440 و1024 بالعربية و390 بالإنجليزية؛ حفظ بريد صحيح، العودة لأعلى القسم، إنشاء متجر، إلغاء وEscape، حذف، تحديث الصفحة، حذف آخر متجر ثم الإنشاء مجدداً. دون أخطاء صفحة أو تمرير أفقي.
- اختبارات البائع السابقة: نجحت على المقاسات السبعة، مع CRUD والصور والمخزون والطلبات والترحيل المحلي.
- PostgreSQL محلي معزول: اختبارات 4B الأربع عشرة، ثم اختبار حذف خاص مع طلب وبند طلب وشكوى مرتبطة، ورفض بائع آخر والعميل، وإخفاء العرض العام، وثبات السعر والمخزون والحالة التاريخية، ومنع استعادة المتجر عبر CRUD البائع، وإعادة استخدام حد المتاجر.

اختبارات SQL تستخدم Auth/Storage محليين بديلين؛ ليست جلسات Supabase مستضافة أو JWT حقيقية. لم تختبر عملية حذف على بيانات مستخدم حقيقية ولم تُحذف بيانات إنتاجية.
