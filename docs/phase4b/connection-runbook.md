# 4B — الربط الآمن وبيئة Node المنفصلة

## الوضع الحالي

لا توجد في البيئة بيانات Supabase أو أسرار مرتبطة أو Node Staging خارجي. التطبيق الجديد مدخل Next.js داخل **المستودع الحالي** في `staging/`، ويستعمل dependencies والأصول والخطوط وCSS والهوية الحالية. ليس مستودعاً أو منصة جديدة. لا يزال `next.config.ts` الأصلي و`.openai/hosting.json` كما هما، ولم يُنشر شيء فوق الرابط الحالي.

```bash
npm ci
npm run staging:build
npm run staging:start
```

الخادم المحلي: `http://127.0.0.1:3100`. المخرج `.next/standalone/staging/server.js` داخل `staging/`، وملفات build/assets معزولة عن `.next/` و`out/` الأصليين. `staging/serve.mjs` ينسخ assets إلى standalone؛ الأمر المعتمد هو `staging:start`. غياب الاتصال يعرض إعداداً غير مكتمل، ويعطل نماذج Auth، ويرفض الأوامر بـ503 دون بيانات تجريبية بديلة.

التشغيل المحلي اختُبر على Node 24.22.1. للتجربة الخارجية: اختر مضيف Node 22 أو 24 منفصلاً أو استخدم `deployment/Dockerfile.staging` من جذر المستودع. البناء المحلي نجح؛ صورة Docker لم تُبنَ أو تُنشر على مضيف خارجي في هذه الدفعة. لا تغيّر DNS أو النطاق أو إعداد النشر الحالي. وفر HTTPS وعنوان staging ثابتاً قبل إعداد رسائل البريد والـRedirects.

## القيم المطلوبة

نسخة الأسماء في `staging/.env.example`. أدخل القيم في مدير أسرار الاستضافة/إعدادات بيئة Codex الآمنة، أو `staging/.env.local` محلياً دون إضافته إلى Git:

- `SUPABASE_ENVIRONMENT=staging`.
- `SUPABASE_PROJECT_REF` ورابط المشروع القياسي `NEXT_PUBLIC_SUPABASE_URL`؛ يجب أن يتطابقا.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: publishable key أو anon JWT فقط. الكود يرفض secret/service_role في هذا الحقل.
- `APP_ORIGIN`: أصل HTTPS لبيئة Node التجريبية، دون path. HTTP مسموح فقط للـlocalhost.
- `RECOVERY_COOKIE_SECRET`: قيمة عشوائية مستقلة قوية، مثلاً 32 بايت عشوائية أو أكثر. تحفظ على الخادم فقط ومتطابقة بين replicas. لا تنسخها من مفتاح Supabase.
- `SUPABASE_SERVICE_ROLE_KEY`: سر خادمي لبوابة Storage فقط، بعد التحقق من المستخدم والملكية؛ لا تحتاجه القراءة العامة أو مسارات Auth. غيابه يبقي رفع الملفات غير متاح.
- `SUPABASE_DB_URL`: للمشغّل وأداة تعيين المسؤول فقط؛ لا تستخدمه واجهات الويب ولا المتصفح.

لا تضع أسراراً في المحادثة أو arguments أو `.env.example` أو `NEXT_PUBLIC_*` أو Docker build args. مجلدات الأسرار وbuild/assets مستبعدة من Git وDocker. لا توجد قيم حقيقية في هذه الحزمة. علم staging وتطابق ref حواجز ضد الأخطاء، وليسا اكتشافاً تلقائياً بأن مشروع Supabase المختار ليس إنتاجياً؛ على المالك التحقق من المشروع نفسه.

## إعداد Supabase Staging بالترتيب

1. أنشئ مشروعاً مستقلاً فارغاً أو راجع المشروع القائم ونسخته الاحتياطية ومهاجراته. لا تستخدم مشروع الإنتاج ولا reset عليه.
2. اربط CLI بمشروع staging المراجع باستخدام تسجيل دخول تفاعلي آمن. راجع `db push --dry-run`، ثم طبّق migrations من 4A والملف `202611170004_auth_catalog.sql` على هذا المشروع فقط. **لم تنفذ هذه الخطوة على مشروع مستضاف بعد.**
3. شغّل seed المرجعي عند الحاجة للفئات. لا تنشئ هويات من localStorage أو تستورد أي أدوار أو جلسات تجريبية.
4. اضبط Auth Site URL إلى APP_ORIGIN، واسمح فقط بمساري `/auth/confirm/` و`/auth/callback/` على الأصل المطلوب. فعّل Email Confirmations، وجهز SMTP لرسائل الاختبار الفعلية وحدود Auth المناسبة.
5. قالب تأكيد البريد يربط إلى `{{ .SiteURL }}/auth/confirm/?token_hash={{ .TokenHash }}&type=email`، وقالب استعادة كلمة المرور إلى `{{ .SiteURL }}/auth/confirm/?token_hash={{ .TokenHash }}&type=recovery`. لا تجعل query `next` دليلاً على الاستعادة. مسار PKCE callback متاح للتأكيد العادي فقط؛ لا يمنح صلاحية تغيير كلمة المرور.
6. أنشئ حساب المالك الأول كـCustomer من واجهة staging وأكّد بريده. يظهر معرف المستخدم في Supabase Auth؛ لا تنشئ مسؤولاً عن طريق metadata أو زر التسجيل.
7. شغّل أداة bootstrap الموضحة أدناه من بيئة مشغّل موثوق. تُثبت علامة staging في قاعدة البيانات وتعيّن أول مسؤول في المعاملة نفسها. قبل هذه العلامة، وظائف بيانات 4B مغلقة. الحسابات الجديدة تبقى Customer حتى يختار المستخدم فتح حساب Seller ويكون بريده مؤكداً.
8. بعد الربط، أعد توليد أنواع Supabase الرسمية وقارنها بالامتداد المحلي في `staging/lib/database.ts`. افحص grants وRLS وسياسات Storage على **JWT حقيقي**، وليس SQL harness فقط.

## أول مسؤول — أداة تشغيل وليست endpoint

الأمر التالي لا يحتوي كلمة مرور أو مفتاحاً؛ يجب أن تكون أسرار DB موجودة بالفعل في مخزن أسرار العملية:

```bash
npm run staging:bootstrap-admin -- --project-ref YOUR_STAGING_REF --user CONFIRMED_USER_UUID --reason "تعيين المالك الأول في بيئة الاختبار" --confirm-staging --mark-staging
```

الأداة تتحقق من وضع staging وتطابق ref مع مضيف/مستخدم اتصال Supabase، وتستخدم TLS موثقاً ومعاملة وparameters، ولا تطبع DSN أو أسراراً. الدالة في `app_private` غير مكشوفة ولا يستطيع anon/authenticated/service_role تنفيذها. ترفض المستخدم غير المؤكد أو غير الفعال، وترفض إنشاء «أول مسؤول» إضافي إذا وجد مسؤول نشط. تُسجل الأدوار والصلاحيات وسبب القرار. إذا كان المشروع يحوي مسؤولاً مسبقاً، لا تعاود bootstrap؛ راجع المشغّل لتثبيت علامة staging دون تغيير ذلك المسؤول.

اختُبرت هذه الضوابط في PostgreSQL المحلي فقط. **لم تُشغّل الأداة على قاعدة Supabase مستضافة.**

## الجلسات والأمان

عمليات Auth عبر خادم Supabase SDK مع Cookies من نوع HttpOnly/SameSite=Lax/Secure على HTTPS، و`getUser()` للتحقق؛ لا يعتمد التفويض على `getSession()` أو user_metadata. `proxy.ts` يجدد الجلسة قبل SSR، وكل أمر يتحقق مستقلاً من المستخدم ودوره. الصفحات الخاصة وAPI لا تُخزّن في cache مشترك.

ضبط Origin يمنع طلبات الكتابة عبر موقع آخر، والتحويلات الخارجية غير مقبولة. الاستعادة تحتاج verifyOtp(type=recovery) ثم إثبات HMAC مرتبط بالمستخدم ومحدود بعشر دقائق؛ لا يسمح login العادي أو `next=/update-password` بتوليد الإثبات. بعد تغيير كلمة المرور يُطلب إنهاء الجلسات. انتهاء رموز الوصول الحالية يخضع لسياسة Supabase؛ global logout ليس وعداً بإلغاء كل JWT فوراً. اضبط العمر والحدود في Auth حسب اختبار staging.

Auth لديه حد إضافي داخل عملية Node؛ هذا ليس rate limiter موزعاً. RPCs لديها حد معاملات لكل مستخدم في PostgreSQL. عند نشر عدة replicas، اضبط حد الطلبات في بوابة الاستضافة وAuth، وحدود body/time/concurrency على مسار الرفع. لا تسجل كلمات المرور أو Cookies أو query token_hash/code في access logs. لا تستخدم next dev مع أسرار حقيقية في سجلات مشتركة.

## Storage

رفع الملفات المباشر للمستخدم مغلق في 4B. المسار الخادمي يتحقق من جلسة حقيقية وملكية المتجر/المنتج، ويحجز حداً للرفع في DB، ويحد body، ويفحص توقيع نوع الصورة ويعيد ترميزها لإزالة metadata. يستخدم مفتاح الخادم فقط للوصول إلى واجهة Storage، ولا يعيده إلى العميل ولا يكتب به بيانات تجارية.

المستندات خاصة، وصور الكتالوج لا تُقرأ عاماً إلا عند تحقق شروط العرض في RLS. التنزيل بعد فحص الصلاحية يحصل على رابط موقّع بعمر 60 ثانية؛ المستندات تُنزّل attachment. قد يبقى الرابط الموقّع صالحاً حتى انتهاء مدته بعد تغيير الصلاحية.

ملفات PDF تحفظ كمسودات غير معتمدة وخاصة؛ لا يوجد antivirus/CDR في هذه البيئة، ولا ادعاء بأنها سليمة. يلزم تكامل فحص موثوق قبل اعتماد المستندات أو الاستخدام الإنتاجي. اختبارات HTTP للرفع والتوقيع والـMIME والحجم على Supabase الحقيقي معلقة حتى الربط.
