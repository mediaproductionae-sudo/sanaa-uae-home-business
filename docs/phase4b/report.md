# تقرير 4B — تجهيز Supabase Authentication & Store Data

تاريخ المراجعة: 17 نوفمبر 2026، بتوقيت الإمارات.

## الحالة الدقيقة

**أُنجز الكود والإعداد والتشغيل المحلي والاختبارات المتاحة. الربط الفعلي والقبول الكامل لـ4B معلقان.** لا توجد بيانات مشروع Supabase أو أسرار أو مضيف Node staging خارجي في البيئة. لم أفترض وجود حساب، ولم أنشئ مشروعاً خارجياً، ولم أطبق migrations على أي قاعدة مستضافة، إنتاجية أو تجريبية. اختبار JWT الحقيقي مسجل `not_run` وليس نجاحاً.

المشروع نفسه استُخدم دون إعادة بنائه أو استبدال الإطار. تطبيق staging هو مدخل Next.js مستقل داخل `staging/` في المستودع نفسه، مع نفس dependencies والأصول والخطوط وCSS والهوية. نقطة الرجوع `backup/before-phase4b` عند التزام 4A: `4b3020e504aa35ecdb71388e0f3551bce1f39be7`.

لم تتغير ملفات `app/` أو `components/` الأصلية أو `next.config.ts` أو `.openai/hosting.json`. لا نشر فوق الرابط الحالي، ولا تغيير للنطاق أو الجمهور أو الأسرار الحالية. لم تُمسح أو تُستورد بيانات localStorage؛ الواجهات القديمة ما زالت DEMO كما كانت. تطبيق staging لا يستخدمها كمصدر لحساباته أو كتالوجه أو صلاحياته.

## الكود الذي جُهز

| المجال | المخرجات وحدودها |
| --- | --- |
| Node | إعداد `output:'standalone'` وProxy وSSR وAPI Routes ديناميكية، وتشغيل محلي فعلي على Node 24.22.1 والمنفذ 3100؛ إعداد الأصل الثابت بقي مستقلاً |
| Auth | تسجيل Customer/Seller، دخول وخروج محلي/عام، تأكيد بريد وPKCE callback، طلب استعادة وتحديث كلمة المرور، قراءة مستخدم موثوق وتجديد جلسات |
| الجلسات | Cookies خادمية HttpOnly وSameSite=Lax وSecure عند HTTPS، و`getUser()` للتحقق؛ لا اعتماد على localStorage أو metadata للدور |
| الأدوار | signup ينشئ Customer فقط، وSeller اختيار محدود بعد هوية مؤكدة؛ لا تسجيل ذاتي كمسؤول ولا إعطاء Admin عبر metadata |
| البيانات | ملف شخصي من DB، فئات، متاجر ومنتجات عامة، صفحات UUID، إدارة متجر ومنتج/خدمة وأرشفة، فلترة وقراءة محدودة/مؤشرات pagination |
| العرض العام | يقرأ بعميل عام مستقل عن JWT البائع لمنع ظهور مسوداته بسبب صلاحية المالك؛ لا بيانات محلية بديلة عند تعطل الاتصال |
| المتاجر | المتجر الجديد pending/submitted، وعدد المتاجر محدود بخمسة في إعداد staging الحالي؛ قرار عرض الإدارة منفصل عن الترخيص |
| المخزون | تعديل كتالوج البائع يسجل حركة مخزون؛ لا حجز مخزون checkout أو طلبات متعددة البائعين في هذه الدفعة |
| الإدارة | قائمة متاجر مراجعة أساسية مرتبطة بـDB ومحمية بالدور والصلاحية؛ لا لوحات مالية تشغيلية أو اختيار دور إداري من الواجهة |
| Storage | بوابة رفع خادمية بعد JWT والملكية وحد رفع DB، وتعطيل الرفع المباشر من المستخدم؛ صور raster يعاد ترميزها، وملفات خاصة وتنزيل موقّع بعمر 60 ثانية |
| أول مسؤول | أداة مشغّل SQL بمعاملة وعلامة staging وأصل مشروع محدد ومستخدم مؤكد وسبب مسجل؛ لا HTTP endpoint للـbootstrap |

هذه مسارات كود فعلية تستخدم SDK وRPCs، لكنها لم تتصل بمزود Supabase مستضاف حتى الآن. لا تُعد البنية أو TypeScript دليلاً على نجاح البريد أو JWT أو Storage HTTP.

## ملفات قاعدة البيانات والصلاحيات

المهاجرة الرابعة `supabase/migrations/202611170004_auth_catalog.sql` تضيف حقلي شعار/غلاف المتجر، وجدولي تشغيل خاصين غير مكشوفين للـAPI، وRPCs محددة للمستخدم المؤكد: الانضمام كبائع، حفظ الملف الشخصي والمتجر والمنتج، الأرشفة، حجز حد الرفع، تسجيل metadata للملف، ومراجعة عرض المتجر.

تظل الجداول العامة الخمسون وقيود 4A قائمة. سياسات القراءة وعزل المالك قائمة، والكتابة المباشرة القديمة لبعض الأعمدة/Storage أُغلقت لصالح المسارات المحددة. كل أمر يتحقق من المستخدم المؤكد وفعاليته والملكية، ويحتاج علامة staging في القاعدة. لا تعديل لحالة الترخيص أو إخفاء الإدارة عن طريق بيانات البائع.

لم تُفتح أي صلاحية كتابة مالية أو دور إداري للمتصفح. `service_role` لا يُستخدم لكتابة بيانات الأعمال؛ factory الخادم يعيد واجهة Storage فقط بعد التحقق من المستخدم والملكية. جميع وحدات المفاتيح/الخدمة معلّمة `server-only`، وفُحصت حزم المتصفح لغياب وحدات الأسرار.

## الصفحات والمسارات الجديدة في مدخل staging

- `/`, `/products/`, `/stores/`, `/categories/`, `/product/<uuid>/`, `/store/<uuid>/`.
- `/login/`, `/register/`, `/confirm-email/`, `/forgot-password/`, `/update-password/`, `/profile/`, `/setup/`.
- `/seller/dashboard/`, `/seller/store/`, `/seller/products/`, `/seller/documents/`.
- `/admin/dashboard/` لإدارة عرض المتاجر في 4B.
- `/api/auth/*`, `/api/catalog/*`, `/api/storage/upload/`, `/auth/confirm/`, `/auth/callback/`, `/media/*`.

الشاشات الأصلية على الرابط الحالي لم تُستبدل. لوحات staging تقدم بيانات 4B فقط؛ لا تعرض أرقام مبيعات أو عمولات محلية باعتبارها أرقام DB حقيقية. الطلبات والدفع والتوصيل والعمولات التشغيلية ليست ضمن هذا المدخل؛ لم يبدأ 4C.

مقاسات واجهة staging: 1920×1080، 1440×900، 1366×768، 1024×768، 820×1180، 390×844، 360×800، بكثافات بكسل 1/2/3. الفحص Chromium بمحاكاة أحجام ولمس؛ ليس أجهزة فعلية أو Safari. فحص الواجهة أجري في حالة غياب الاتصال؛ النماذج المحمية بعد دخول حقيقي تحتاج الاختبار اللاحق.

SQL/RLS اختُبرا بمحرك PostgreSQL حقيقي مع عقد Auth/Storage محلي وهمي. هذه ليست JWTs حقيقية ولا GoTrue/PostgREST. اختُبرت حماية أول مسؤول وعزل بائعين ومنع العميل من منح دور أو تعديل متجر آخر وقيود التعديل والمخزون وإغلاق الرفع المباشر والحساب غير المؤكد/المعلق وحدود DB، دون أي قاعدة إنتاجية.

## ما لم يُختبر أو يُفعّل

- الاتصال بمشروع Supabase Staging مستقل وتطبيق المهاجرات عليه.
- تسجيل عميل/بائع حقيقي عبر البريد، SMTP، تأكيد البريد، واستعادة كلمة المرور فعلياً.
- JWT حقيقي وعزل RLS عبر PostgREST، وتجديد Cookies وانتهاء/إلغاء جلسات حقيقية.
- الرفع الفعلي إلى Storage والتنزيل والتوقيع والصلاحية على خدمة Supabase.
- تشغيل أداة أول مسؤول على قاعدة مستضافة؛ اختبارها كان SQL محلياً فقط.
- بناء/نشر Docker على مضيف staging خارجي، وHTTPS والـreverse proxy هناك.
- الفحص ضد الفيروسات أو CDR لـPDF: المستندات خاصة ومسودة وغير معتمدة، والواجهة توضح ذلك؛ يلزم فحص موثوق قبل اعتمادها أو استخدامها إنتاجياً.
- حد Auth داخل Node ليس موزعاً؛ يلزم حد إضافي في بوابة الاستضافة/Auth عند تعدد replicas. RPCs لها حد DB مستقل.
- إعادة إبطال الروابط الموقّعة التي أُصدرت سابقاً ليست فورية؛ عمرها 60 ثانية. global logout يخضع لعمر JWT وسياسة المزود.
- متغيرات الإعداد الصحيحة شكلياً لا تثبت الاتصال. لا يدّعي `/setup/` نجاح الاتصال لمجرد وجودها.

لا أخطاء بناء أو TypeScript أو اختبارات محلية متبقية معروفة. عدم الاتصال واختبارات التكامل غير المنفذة شروط معلقة، وليست اختبارات ناجحة أو جاهزية إنتاجية مكتملة.

## الملفات

مضافة: `staging/app/` و`staging/components/` و`staging/lib/` و`staging/tests/`، وملفات Next/TypeScript/env/prepare/serve/bootstrap داخل `staging/`؛ المهاجرة الرابعة؛ `deployment/Dockerfile.staging`؛ وتقارير `docs/phase4b/`.

معدلة: `package.json` و`package-lock.json` لإصدارات SDK مثبتة (`@supabase/ssr 0.12.7`, `@supabase/supabase-js 2.119.0`, `server-only 0.0.1`, `sharp 0.35.5`, و`pg 8.23.1` كأداة تطوير)، و`.gitignore` و`.dockerignore` للعزل ومنع نسخ الأسرار، و`tsconfig.json` لفصل TypeScript staging، وملفا harness/reset المحليان لاختبارات 4A/4B.

لا تغييرات في `app/` أو `components/` الأصلية أو `next.config.ts` أو `.openai/hosting.json`. حزمة المراجعة تحتوي تغييرات المصدر فقط، بلا `.env.local` أو node_modules أو build أو أسرار أو بيانات متصفح؛ تطبق فوق المشروع الحالي وليست مشروعاً مستقلاً جديداً.

## المطلوب لإكمال الربط

1. أنشئ/اختر مشروع Supabase **staging مستقلاً** وحدد Project URL وProject Ref والمفتاح العام.
2. اختر مضيف Node staging وأصل HTTPS منفصلاً، واضبط Site URL/Redirects وSMTP وقوالب التأكيد والاستعادة داخل Supabase.
3. ضع مفاتيح الخادم وDB وRECOVERY_COOKIE_SECRET في مخزن أسرار آمن أو إعدادات البيئة؛ **لا ترسل كلمة مرور أو service_role في المحادثة**.
4. اتبع `connection-runbook.md` لتطبيق المهاجرات على staging فقط وإنشاء Customer المالك ثم تعيين أول مسؤول بأداة المشغّل.
5. جهز أربعة حسابات اختبار مؤكدة ومخصصة، ثم نفذ اختبار JWT والسيناريوهات اليدوية في `testing.md`.

لا نحتاج موافقة جديدة على نطاق 4B الذي اعتمدته؛ التوقف الآن بسبب غياب الاتصال والاستضافة، وفق شرطك. لا يبدأ 4C ولا نشر على الرابط الحالي ضمن استكمال هذا الربط.
