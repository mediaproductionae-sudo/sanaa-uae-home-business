# ملف البائع الشخصي — تسليم 25 نوفمبر 2026

## النطاق

المصدر هو ملف المالك «المعلومات الشخصية للبائع.docx». يعرض `/profile/` للبائع نموذجاً مستقلاً بأقسام البيانات الأساسية والعنوان والبنك والضريبة. لا تتغير واجهة المتعامل أو الشعار أو إعدادات المتاجر والتوصيل. تسجيل البائع يوجهه إلى `/profile/?onboarding=seller` بدلاً من شاشة المتجر. عند اشتراط تأكيد البريد، ينتقل إلى شاشة الملف برسالة تأكيد ثم يكمل بعد التأكيد وتسجيل الدخول؛ لا نتجاوز شرط وجود جلسة موثوقة لحفظ معلومات شخصية.

| الحقل | القاعدة |
|---|---|
| الاسم الكامل بالعربية والإنجليزية | إلزاميان عند إكمال الملف، حتى 120 حرفاً لكل اسم |
| البريد الإلكتروني | من Auth، للقراءة فقط، تظهر حالة التحقق الفعلية |
| الهاتف | E.164، مع تحويل أرقام الهاتف المحلية الإماراتية؛ OTP من Supabase Auth |
| الصورة الشخصية | اختيارية، PNG/JPEG/WebP، حتى 5 MB |
| الإمارة والمدينة/المنطقة واسم البناية | إلزامية عند الإكمال |
| رقم البناية | اختياري |
| اللغة المفضلة | عربية أو إنجليزية، بيانات الحساب مستقلة عن لغة الواجهة |
| تاريخ التسجيل | من Auth، للقراءة فقط، بتوقيت الإمارات |
| اسم صاحب الحساب البنكي | يُخزن الآن، وإلزامي قبل أي صرف مستقبلي؛ لا عمليات صرف في هذه الدفعة |
| اسم البنك وIBAN | إلزاميان عند إكمال الملف؛ تحقق AE وطول 23 ومحسوب mod-97 |
| شهادة الحساب | عند الحاجة، PDF/PNG/JPEG، حتى 5 MB |
| VAT/TRN | نعم/لا، رقم 15 خانة إلزامي عند اختيار نعم؛ يُفرَّغ TRN عند اختيار لا وحفظ النموذج |

تتوفر مسودة تحفظ ما أُدخل، وإكمال يتحقق من جميع الحقول الإلزامية ومن البريد والهاتف على الخادم. لا يعني اكتمال المعلومات اعتماد بائع أو متجر أو ترخيص. تظل عمليات الموافقة والصرف خارج هذا التغيير، ولا تُمنح أدوار جديدة من نموذج المعلومات.

## الربط المطلوب من Lovable

1. اسحب آخر `main` وراجع `docs/sql/20261125_seller_personal_profile_review.sql` مقابل مخطط القاعدة الفعلي. الملف **للمراجعة فقط**، خارج أدلة المهاجرات المدارة التزاماً بـAGENTS.md. حوّله إلى migration جديدة وفق مسار Lovable وطبّقه بعد مراجعة المالك في البيئة المناسبة. لا تعِد تشغيل مخطط 0000 أو المهاجرات القديمة، ولا تمسح بيانات حالية.
2. ينشئ SQL جدولَي `seller_personal_details` و`seller_bank_details` وربطهما بمالكهما `profiles.id`؛ ودالتَي `sanaa_seller_personal_get` و`sanaa_seller_personal_save`، ومساعدَي تحقق خاصين، وحاوية `seller-profile-private` الخاصة وسياسات الملفات. لا يغيّر الجداول المالية أو سياسات التوصيل أو أدوار الحسابات الحالية.
3. فعّل Phone Auth ومزوّد SMS المناسب في إعدادات Supabase، واحفظ مفاتيحه في إعدادات الخادم فقط. تُستعمل `auth.updateUser({phone})` ثم `verifyOtp({type:'phone_change'})`. إذا تطلبت سياسة تبديل الهاتف التحقق من رقمين، لا تُعرض حالة نجاح نهائي إلا عندما يعيد الخادم الرقم الجديد مؤكداً. عند غياب المزوّد يظهر فشل حقيقي، ولا ننشئ OTP وهمياً.
4. احتفظ بتأكيد البريد. تأكد من سماح قائمة إعادة التوجيه بعنوان النطاق الحالي `/profile/` و`/profile/?onboarding=seller`، دون إضافة نطاقات غير موثوقة.
5. حدّث أنواع Supabase المُولَّدة بالطريقة المدارة إن لزم؛ لم تُعدَّل الملفات المُولَّدة يدوياً. الكود الجديد يستدعي RPCs عبر عميل Supabase العام بهوية المستخدم الحالية.
6. ابنِ وانشر على الموقع الحالي، ثم اختبر بحسابَي بائع ومتعامِل حقيقيين في Staging وJWT حقيقي قبل اعتماد الربط على التشغيل. لا تطلق أي عمليات مالية لهذه الخطوة.

إذا لم يُطبَّق SQL، تعرض الصفحة رسالة «تحتاج المنصة إلى تفعيل إعدادات الملف الشخصي على الخادم» وتمنع الحفظ؛ لا تحفظ البيانات الشخصية في localStorage أو تستبدل الخطأ بنجاح وهمي.

## الصلاحيات والمرفقات

- الخادم يستخرج `auth.uid()`، ويتحقق من حساب نشط ودور بائع وملف بائع فعلي. لا تُقبل هوية مستخدم أو دور أو تاريخ تسجيل أو علامة تحقق من المدخلات.
- القراءة المباشرة للجدولين لصاحبهما النشط فقط بواسطة RLS. لا صلاحية إدراج أو تعديل مباشر؛ الحفظ عبر RPC ضيقة ومعاملة واحدة للبيانات الأساسية والبنكية. لا يوجد وصول عام لبيانات البنك، ولا تستخدم service_role في هذه الميزة.
- لا يسمح RPC بالربط بملف مفقود أو بملف تحت مسار حساب آخر. تُرفع الملفات إلى `<auth.uid()>/avatar/…` أو `<auth.uid()>/bank/…` بأسماء UUID؛ تُفحص الأحجام والأنواع والتوقيعات في العميل، وتفرض الحاوية حداً للأنواع والأحجام. هذا ليس فحص برمجيات خبيثة على الخادم.
- الحاوية خاصة، وروابط العرض موقعة لمدة 60 ثانية. لا سياسة UPDATE للملفات. لا يمكن حذف ملف لا يزال مرتبطاً بالملف الشخصي من خلال سياسة الحذف.
- عند استبدال مرفق أو إلغاء عملية حفظ قد يبقى ملف خاص غير مرتبط. يلزم وضع سياسة احتفاظ وتنظيف لاحق للملفات غير المرتبطة، مع مراعاة عدم حذف المرفقات المرجعية. لا تنفذ هذه الدفعة حذفاً آلياً لمستندات المستخدمين.
- الاسم البنكي شرط مطلوب قبل تشغيل أي صرف مستقبلي. لم تتغير إجراءات الصرف الموجودة، ويجب أن يتحقق خادم الصرف منه ومن متطلبات KYC ذات الصلة عند تنفيذ تلك المرحلة. اكتمال هذا النموذج وحده لا يجيز الدفع.

## الاختبارات الفعلية

- 9 اختبارات تحقق للحقول والأنواع والاسمين وIBAN وTRN والتلاعب بالحقول وحجم/نوع المرفقات.
- 12 اختبار PostgreSQL في قاعدة مؤقتة معاد بناء مخططها داخل الحاوية المحلية الموجودة `sanaa-phase4a-pg`، دون اتصال بقاعدة مُدارة. شملت تشغيل SQL مرتين، RLS بين بائعين، منع المتعامل/الزائر/المعلق، حقول هوية وتحقق مزورة، شرط البريد والهاتف، رفض IBAN وTRN غير صحيحين، منع تحديث مباشر، وعزل مسارات Storage وحماية المستند المرجعي ومنع الاستبدال. تستعمل الاختبارات claims جلسة قاعدة محلية، **وليست JWT صادرة عن Supabase Auth**.
- 14 فحص متصفح لمقاسات 1920×1080 و1440×900 و1366×768 و1024×768 و820×1180 و390×844 و360×800 باللغتين. اختُبر حفظ مسودة واستعادتها بعد التحديث، حالات OTP الفاشلة والخاطئة والناجحة، عدم فقد بيانات غير محفوظة عند التحقق، الإكمال، VAT/TRN، توقيع الملف ومساره، وتعطل المخطط بوضوح. استُعملت استجابات شبكة معترضة ومعزولة.
- اختبارات متصفح لمسار التسجيل مع تأكيد البريد، وعرض النموذج للبائع المسجل، وبقاء نموذج المتعامل السابق.
- شُغلت TypeScript وbuild بعد التنفيذ. نتائج إعادة الفحوصات العامة مدونة في LOVABLE_HANDOFF.md.

لم يُطبَّق SQL على Supabase المُدار، ولم يُختبر إرسال بريد أو SMS حقيقي أو تسجيل بائع حقيقي أو رفع ملف إلى حاوية مُدارة أو JWT حقيقي. لا تدّعِ جاهزية تشغيل هذه الروابط قبل إعدادها واختبارها في Lovable.

لإعادة الاختبارات المحلية، شغّل اختبارات الحقول بواسطة `npm exec vitest run src/seller-profile/schema.test.ts`. اختبارات القاعدة الاختيارية تتطلب حاوية اختبار محلية قائمة بالاسم المذكور ثم `SELLER_PROFILE_TEST_DOCKER=sanaa-phase4a-pg npm exec vitest run src/seller-profile`. لا تستخدم عنوان قاعدة منشورة.
